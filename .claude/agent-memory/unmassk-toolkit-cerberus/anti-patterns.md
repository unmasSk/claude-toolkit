## Docs promise "persisted verbatim" for a multi-line block, but the persistence layer is single-physical-line

Confirmed 2026-07-25, unmassk-toolkit "dead-end memory loop" round (`c9939f3..HEAD`, Bilbo/Cerberus/Gitto crew, `memo(deadend/<subsystem>)` feature). `agents/bilbo.md:144` and `skills/unmassk-gitmemory/SKILL.md:167` both say the multi-line, per-symbol `DEAD-ENDS` block (question + N "ruled out: NOT in `symbol`" lines + `verdad-en: <sha>`) is "persisted verbatim" by the orchestrator. But the ONLY persistence surface is the `Memo:` commit trailer, which is structurally one physical line everywhere in the codebase: `lib/parsing.py::parse_trailers()` matches `^(Key):\s*(.+)$` per line and BREAKS the bottom-up scan at the first non-matching line; both `pre-`/`post-validate-commit-trailers.py` do `trailers["Memo"].split(" - ", 1)` on a single string; `bin/git-memory-commit.py::build_commit_message()` builds one list element `f"{key}: {value}"` per `--trailer`; and `lib/recall.py::_format_block()` (feeds the recall-injection hook) emits ONLY `trailers[kind]` — the free commit BODY text is never read back by recall(), so anything not squeezed into the single trailer line is invisible to the consumer forever. Confirmed via a full read of the round-trip: no test in the round exercises a multi-symbol block (the one new test, `test_memo_category_deadend_contract.py`, uses a single-line stand-in). This is a real producer→consumer format gap under this project's own threat model (silent memory-fidelity loss), not attacker-relevant.

Check pattern: whenever a new doc/skill claims a rich, multi-line, structured block will be "persisted"/"stored"/"round-tripped" through a git-memory commit trailer, grep the trailer-parsing regex (`parse_trailers`/`scan_trailers_memory`) and the trailer-consuming recall function to confirm they support more than one physical line per key before accepting the claim. If they don't, the doc needs an explicit compression step (with a worked example) and a real round-trip test — not just a category-acceptance test with a hand-written single-line stand-in.

## "Mirror" functions drift out of sync on defense-in-depth guards (parse_date / time_ago)

Confirmed 2026-07-08, issue #55 final round (`lib/date_parsing.py::parse_date()` vs `lib/boot_git_checks.py::time_ago()`). Both functions share the same docstring cross-reference ("mirrors the other's ... shape") and got the same `isinstance(str)` + `isascii()` guards added in lockstep across two review rounds. But `parse_date()` also has an explicit `if len(date_str) > 20: return None` length guard (defense-in-depth ahead of `int()`, added for SEC-LOW-002) that was never mirrored onto `time_ago()`. Not a live bug — CPython's own `sys.get_int_max_str_digits()` limit and `datetime.fromtimestamp()`'s `OverflowError` both land inside `time_ago()`'s existing except tuple, so it fails safe by accident, same as `parse_date()` did before its own explicit guard existed (see `TestParseDateLengthGuardContract`'s honesty note in `test_date_parsing_epoch_contract.py`).

Lesson: when two functions are documented as mirroring each other and a guard is added to one under an explicit "defense-in-depth, not dependent on interpreter limits" rationale, check whether the twin function needs the identical guard — don't just check that both got the same `isinstance`/`isascii()` treatment. Grep for the guard's own justification comment; if it says "not dependent on X", the other function inherits the same argument.

## tempfile.mkstemp() + os.replace() atomic write silently narrows the destination's permission bits

Confirmed live 2026-07-19, fix-atomic-claude-md-write.md round (`lib/git_helpers.py::_AtomicWriteNoFollowSymlink`). `os.replace(tmp_path, final_path)` swaps the whole inode, so the destination inherits the TEMP file's mode, not the ORIGINAL file's. `tempfile.mkstemp()` always creates at `0o600`. Reproduced: a CLAUDE.md checked out at the normal `0o644` (typical git-checkout mode) drops to `0o600` after a single managed-block update via the new atomic helper — while the OLD non-atomic `open_no_follow_symlink(path, "w")` (`O_TRUNC` on an EXISTING file, mode arg only applies at `O_CREAT`) correctly preserved `0o644`. This is a real, silent side effect nobody asked for — a plan that says "only change HOW it's written, not WHAT" implicitly includes the file's permission bits as part of "what's already there."

Why the mirrored pattern (`lib/boot_fetch_stamp.py::_write_own_stamp()`) never hit this: that target file is ALWAYS internal/generated-only (never a pre-existing user-editable file with meaningful prior permissions) and DELIBERATELY calls `os.chmod(final_path, 0o600)` after `os.replace()` as an explicit hardening choice for a purely-internal state file. Reusing "temp+replace, mirroring boot_fetch_stamp.py" for a normal git-tracked, user-facing config file (CLAUDE.md) without also carrying over an explicit permission-preservation step regresses silently — git itself won't show it in `git diff`/`git status` (git only tracks the executable bit, not full POSIX mode), so nothing in the ordinary dev workflow would ever surface this.

Check pattern: whenever a review sees a NEW `tempfile.mkstemp()` + `os.replace()` atomic-write helper applied to a file that pre-existed with attacker/tooling-relevant permissions (a normal user file, not an internal-only generated one), verify live: `chmod` the pre-existing file to something other than mkstemp's default before triggering a write, then check the post-write mode. If the helper mirrors an existing internal-only pattern, check whether that pattern's permission handling (e.g. an explicit post-replace `chmod`) was a DELIBERATE choice for that target's specific nature, not something safe to skip when reusing the pattern for a different kind of file.

## New "ask before proceeding" branch omits the sibling guard's lookup-failure check → fails OPEN instead of closed

Confirmed live 2026-08-04, feat/memoria-v2 `bin/memory/remove.py::main()` (P5 incident-close-question feature, `--restriction` no longer `required=True`). The new branch (`elif args.restriction is None and args.id.startswith("I-"):`) calls `query.by_id(args.id)` and only asks the mandated P5 question `if incident is not None`. When `query.by_id` returns `None` — id genuinely missing, OR the index (`INCIDENTS.md`) and git log (the actual source `query.by_id` scans) have drifted apart — the branch does **nothing**: no print, no return, falls straight through to `notes.close()`. Reproduced live by desyncing the index (renaming the id inside `INCIDENTS.md` only, leaving the real commit under the old id): `remove.py <desynced-id> "..."` (no `--restriction`) exits **0** with `"✅ <id> archivada"` — the P5 wall-question never fires, no warning at all. Contrast with the *sibling* guard three functions above it in the same file, `_guard_restriction_new()`, which explicitly checks `query.by_id() is None` and prints a clear stderr rejection before returning 1 — the new branch was written next to a guard that already solved this exact problem and didn't reuse it.

Lesson: whenever a new branch adds "look something up, then act on it only if found" (a `query.by_id`/similar `Optional`-returning lookup used as an implicit gate), check what happens on the `None` path explicitly — don't assume the reviewer/tests will only exercise the happy path. If a **sibling function in the same file** already guards the identical lookup with an explicit fail-loud `None` check, flag it as a missed reuse the moment the new branch's `None` path is silent. This is exactly this project's own threat model (system-against-itself, silent bypass of a mandated question) — not a lab case; a mistyped id or an index/git-log drift are both realistic ways to hit it.

Check pattern: for any new `if <lookup>(...) is not None:` gate added around a "must ask/must reject" rule, grep the same file for an existing guard over the same lookup function and diff their `None`-handling. If the existing guard fails loud and the new one doesn't, it's a T1 finding (silent bypass of a safety rule), not a nitpick.

## Trailer content validation runs on the pre-sanitize value, not the value that actually gets committed

Confirmed live 2026-07-25, `bin/git-memory-commit.py::_validate_trailer_content()` (new Memo:/Remember: content gate, wip `e2dafbe`). The non-empty-description check (`not parts[1].strip()`) runs on the RAW `--trailer` value straight from argv. But the value that is actually written into the commit is `sanitize_trailer_value(value)` (called later, inside `build_commit_message()`), which turns control bytes (`\x1b`, `\x7f`, `\x1c-\x1f`, `\x85`, CR/LF, etc.) into spaces and then `.strip()`s the result. A description made ONLY of control bytes (e.g. `"preference - \x1b\x1b\x1b"`) is non-empty (and non-whitespace, since `\x1b` fails `str.isspace()`) under the raw check, so it PASSES validation — but collapses to an empty string after sanitize, producing a committed trailer of `Memo: preference -` with no description at all. Reproduced end-to-end through the real wrapper (scratch repo, `rc=0`, commit created, `git log -1 --format=%B` shows the empty trailer) — this is exactly the "silent inert memory" failure class the whole validation feature was built to close, just reached via a different input shape (control bytes) than the one that was tested (missing separator / out-of-enum category / plain empty string).

Why this is easy to miss: the RED-test docstring and the happy-path GREEN controls only exercise plain-ASCII descriptions; nothing in the contract constructs a description that is non-empty pre-sanitize but empty post-sanitize. `sanitize_trailer_value()` itself is well-documented (its own docstring lists every byte class it collapses), but nothing connects "this sanitizer runs downstream of validation" to "therefore validation must check the sanitized value, not the raw one."

Check pattern: whenever a new validation gate checks a raw value that is later passed through a sanitizer/normalizer before being persisted, verify the gate operates on the POST-sanitize value (or re-validates after sanitizing) — not the pre-sanitize argv/input value. Concretely: grep for every `sanitize_*`/`normalize_*` call downstream of the new validation in the same function/call chain, then construct an input that is empty/invalid only AFTER that transform (e.g. control-byte-only string, or a string that only becomes empty after whitespace-collapsing) and confirm the gate still rejects it.

`trap "rm -rf $TEMP_VENV" EXIT` expands the variable at definition time. If it contains spaces this silently deletes the wrong directory. Always use single quotes for trap bodies:

## set -- "${POSITIONAL_ARGS[@]}" when array may be empty

Under `set -u`, an empty array expansion with `"${arr[@]}"` produces a single empty string argument on some bash versions. Guard with:

```bash
if [ ${#POSITIONAL_ARGS[@]} -gt 0 ]; then

```

## ((...)) arithmetic increment under set -e

`((var++))` exits with code 1 when var is 0 (the result of the expression is 0 = falsy). Under `set -e` this terminates the script. Use `var=$((var + 1))` instead.

Confirmed in ops-cicd Jenkins scripts: `jenkins-best-practices.sh:40,47,54,60`, `jenkins-validate-declarative.sh:37,44,51`, `jenkins-validate-scripted.sh:37,44,51`. All use `((ERRORS++))` / `((WARNINGS++))` etc. as counters starting at 0. The first found issue kills the script silently.

Reference implementation: `jenkins-validate-shared-library.sh` uses `ERRORS=$((ERRORS + 1))` — use this as the correct model.

Note: `jenkins-common-validation.sh` has the same `((var++))` but uses `set -uo pipefail` (no `-e`, intentional) — this is a false positive. Do NOT flag it.

## bash -n with multiple file arguments

`bash -n file1 file2 file3` only checks file1 syntax; file2 and file3 are positional arguments to that check, not independent checks. Correct:

## Python `or`-based defaults replace falsy caller values

`kwargs.get("key") or default` silently replaces 0, empty string, and False with the default even when the caller explicitly passed those values. Use `is not None` instead:

```python
# WRONG
value = kwargs.get("ingestion_rate_mb") or 10

# CORRECT
value = kwargs["ingestion_rate_mb"] if kwargs.get("ingestion_rate_mb") is not None else 10
```

Found in: `loki-generate-config.py` `_generate_monolithic`, `_generate_simple_scalable`, `_generate_microservices`. The fluentbit generator explicitly tests and documents the fix (`TestFalsyDefaults`).

## `exit $?` after a command under `set -e` is unreachable on failure

```bash
some_command "$@"
exit $?   # only reached when some_command succeeds (exit 0)
```

Under `set -e`, if `some_command` exits non-zero, the script is already terminated before `exit $?` runs. Save the exit code explicitly:

```bash
local rc=0
some_command "$@" || rc=$?
exit "$rc"
```

Found in: `shellcheck_wrapper.sh:49` `check_system_shellcheck()`.

## ASCII box line[:85] + '|' truncation pattern

In `skill-search.py` `format_ascii()`, the corpus line is constructed as:
```python
lines.append(f'|  Corpus: {total_skills} skills indexed ...|'[:85] + '|')
```
The intent is to pad to 85 chars. The pattern is fragile: if the raw string is exactly 85 chars, slice returns all 85 then '|' is appended making it 86 chars (one over the box). For skill counts >= 100, the raw string is already 86+ chars and the slice-then-append makes it 86, misaligning the closing border.

Correct pattern: use an f-string with explicit ljust or format spec to 83 inner chars, then wrap in '| ... |'.

## Fallback path-existence flag not reset when the write it guards fails

When a function writes a file inside a `try/except OSError: pass` (silent-fail, correct on its own — the caller must not crash) but sets the "path exists / is available" variable *before* the try block instead of only on successful write, any downstream branch that checks `if path_var: use path_var` cannot distinguish "wrote successfully" from "write failed, pass'd silently." If that downstream branch is a size/budget check that decides between "print everything inline" vs "print a short pointer to the file," a failed write reproduces the exact bug the pointer-file design was meant to fix: the short banner claims the full content is in the file, but the file was never written (first run) or is stale (later runs) — the real content, e.g. the harness-truncation-preventing "Next:" line, is silently lost.

Reproduced live (not just static reading) in `session-start-boot.py:1291-1301`: `boot_log_path` is set right after `if project_root:`, before the `try/except OSError`. `os.chmod(claude_dir, 0o500)` (read-only, simulating disk-full/permission-denied/read-only-fs, e.g. sandboxed CI) + a giant `context()` commit that exceeds `STDOUT_FULL_INLINE_BUDGET_BYTES` (6000) → hook exits 0, prints the "minimal banner" telling Claude to read `boot-log-latest.txt`, but the file does not exist (`os.path.isfile() == False`). No test in `test_boot_output.py` covers this path (grep for OSError/chmod/PermissionError in that file returns nothing) — the entire 42-test contract was RED/GREEN only for the happy path.

Correct fix: only treat the log path as "available" after the `open()`+`write()` inside the try succeeds — e.g. set `boot_log_path = None` initially and only assign the real path on success, or use a separate `log_write_ok: bool` flag; then in the branch condition, treat write failure the same as "no project root" → fall through to printing `full_text` inline unconditionally (safer than pointing at a promise that isn't there), regardless of size.

General rule when reviewing "write full content to file, print short pointer on stdout" fallback designs: always check whether the "pointer is safe to print" condition is coupled to write *success*, not just to whether a path *could theoretically* be computed. Test the OSError branch explicitly (chmod a parent dir read-only, or monkeypatch `open`) — a happy-path-only contract will pass 100% green while reintroducing the original bug under any permission/disk-full condition.
