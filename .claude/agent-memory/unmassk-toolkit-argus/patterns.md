**No external attacker in this repo's model.** CLAUDE.md states this explicitly (re-read and confirmed unchanged 2026-08-25) and it is load-bearing for every audit here: this toolkit is the owner's single-user tool, not a public product. OWASP-style hostile-input findings (injection from an untrusted network caller, auth bypass, CORS, etc.) are dead weight unless the finding is really about the system corrupting/losing its own state. The real threat model is **the system harming itself**: memory loss/corruption, writing outside the project root, a failure that passes silently, a badly-built command that self-executes on internal data.

**`git_helpers.py` is a mature, already-hardened shared library** (re-verified 2026-08-25: `run_git`/`open_no_follow_symlink`/`verify_path_within_project`/`ensure_runtime_dir`/`file_lock` all present and unchanged in shape). `run_git` (`Popen(["git"] + args, ...)`, never `shell=True`, process-group kill on timeout via `start_new_session=True`/`CREATE_NEW_PROCESS_GROUP`), `open_no_follow_symlink` (O_NOFOLLOW / Windows TOCTOU identity check / optional hard-link rejection / atomic replace variant), `verify_path_within_project` + `ensure_runtime_dir` (resolves every intermediate symlinked component, not just the final one) already carry inline `SEC-*`/`ROB-*` comments documenting prior Argus/Moriarty rounds that fixed them. When a new hook reuses these helpers, the read/write-safety half of the audit is usually already closed — verify the *call site* passes the right mode/flags, don't re-derive the primitive's own safety from scratch every time.

**Git argument "literal `--` before caller-influenced paths" convention — the concrete evidence for this is now GONE, principle unverified against any current production call site.** `is_tracked_in_head` (the function this was checked against, `git_helpers.py:1178`) no longer exists: it was deleted in the "fuera el guardián de tests del Stop" cleanup (commits `d70905a`, `5f6b513`), which also removed `hooks/stop-dod-gate.py` entirely. Re-checked 2026-08-25 (`grep -rn 'run_git(\[' lib bin`): every production `run_git([...])` call site left in `lib/`+`bin/` takes only fixed literals (`rev-parse --show-toplevel`, `--is-inside-work-tree`, `for-each-ref --format=...`) — none takes a caller-influenced path string, so there is currently nothing in production code to demonstrate or contradict the convention. Only three remaining `run_git([...])` calls with a literal `"--"` exist at all, and they're in `tests/memory/*.py` against a *different*, test-local `run_git(args, cwd)` (3-value return) defined in `tests/memory/conftest.py:646` — not the shared `git_helpers.run_git`. **Still check for `"--"` before caller-influenced path args on any NEW production `run_git` call site** (the principle — "this string can never be reinterpreted as a git option" — is sound and worth holding new code to), but do not cite `git_helpers.py:1178` or `is_tracked_in_head` as the example again; both are gone.

**`lib/memory/` field round-trip pattern (established `--issue` opened from M-only to all 7 note types, commit `c186aa9`, re-verified 2026-08-25)**: this pipeline enforces "no orphaned field" by construction — `vocabulary.py::FIELDS[name].reader` names the one real reader and the module crashes on import if a type declares a field without one. For `issue` specifically there are exactly three surfaces that must stay in sync, all confirmed type-agnostic (no `note.type == "M"` gate left anywhere in `lib/memory/`, re-grepped 2026-08-25): writer `format.py::_body_field_line`, human report `report_render_note.py::_note_fields`, and the boot safety net `health_plans.py::_issue_commit_dates` (regex-scans raw commit body `^Issue: #(\d+)$`, never calls `format.parse_message`). `validator_issue.py::validate_issue`/`issue_exists` (the real `gh issue view` existence check) never branched on note type either — the only gate that ever blocked non-M types from carrying `--issue` was `vocabulary.TYPES[...].allowed_fields`, now open for all seven (confirmed: `issue` appears in every `allowed_fields` frozenset in `vocabulary.py`). `--issue` is `argparse type=int` at the CLI boundary in `bin/memory/note.py` — never a raw string reaching `gh` or the commit body — so injection-style findings don't apply (consistent with the no-external-attacker note above). **The gap once flagged here — `bin/memory/work.py --issue N` skipping the `gh` existence check — is CLOSED, fixed in the SAME commit `c186aa9` that opened the field**: `work.py` now imports `validator_issue` and calls `validator_issue.issue_exists(args.issue)` before committing (`work.py:53,137-148`), rejecting via `_issue_rejection` when `gh` confirms the issue doesn't exist. Re-verified 2026-08-25 — do not re-flag.

**`file_lock()` (git_helpers.py) is this repo's established fix for cross-process read-modify-write races — 18+ call sites use it** (memory notes/indexes/rules via `gitcmd.file_lock`, `incidents.py`, `install_apply.py`, `session-start-crew.py` via `claude_md_lock_path`, and as of the fix below, `checklist_state.py`). When a load→mutate→save cycle on a shared per-session/per-project file does NOT call `file_lock()` across the WHOLE cycle (not just the final write — `open_no_follow_symlink(..., atomic=True)` only protects a single write from torn/partial content, not two sequential writes racing each other), that omission is a real, checkable regression against the project's own convention. **The `checklist_state.py` instance of this gap (found 2026-08-24 on `lib/checklist_state.py`, hit via `checklist-gate.py`/`skill-checklist-inject.py` racing on `save_registry()`) is now CLOSED**: re-verified 2026-08-25, the module now exposes a `locked()` context manager (`checklist_state.py:139-170`) wrapping `file_lock()` around the full `load_registry()`→mutate→`save_registry()` cycle, with both call sites (`hooks/checklist-gate.py:171`, `hooks/skill-checklist-inject.py:135`) using `with checklist_state.locked(...)` around their read-modify-write. Do not re-flag this exact case; still check any OTHER new module with a load→mutate→save cycle for the same convention.

**`verify_path_within_project()` only guarantees "stays inside project_root somewhere" — it does NOT by itself pin a path to the specific intended subdirectory/file.** A caller-supplied path component (e.g. a session_id) containing `/` or `../` can pass the containment check while still colliding with a sibling file inside the guarded tree ("escapes the project" and "collides within the project" are different bugs — the guard only catches the first). **The `checklist_state.py` reproduction of this (session_id `"foo/../../bar"` aliasing a different registry file, found 2026-08-24) is now CLOSED**: re-verified 2026-08-25, `checklist_state.py:98-112` adds `is_safe_path_component()` (rejects `/`, `\`, `..`, empty) called before every path build (`registry_path()` line 122, `locked()` line 155) — its docstring literally names the `"foo/../../bar"` case this was written against. Do not re-flag this exact case. Still apply the general principle to any NEW path built from an identifier not already validated against a known format (UUID, etc.) upstream — check both failure modes separately.
