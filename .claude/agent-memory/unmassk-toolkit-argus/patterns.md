**No external attacker in this repo's model.** CLAUDE.md states this explicitly and it is load-bearing for every audit here: this toolkit is the owner's single-user tool, not a public product. OWASP-style hostile-input findings (injection from an untrusted network caller, auth bypass, CORS, etc.) are dead weight unless the finding is really about the system corrupting/losing its own state. The real threat model is **the system harming itself**: memory loss/corruption, writing outside the project root, a failure that passes silently, a badly-built command that self-executes on internal data.

**`git_helpers.py` is a mature, already-hardened shared library.** Functions like `run_git` (always `shell=False`, `Popen(["git"] + args, ...)`, process-group kill on timeout), `open_no_follow_symlink` (O_NOFOLLOW / Windows TOCTOU identity check / optional hard-link rejection / atomic replace variant), `verify_path_within_project` + `ensure_runtime_dir` (resolves every intermediate symlinked component, not just the final one) already carry inline `SEC-*`/`ROB-*` comments documenting prior Argus/Moriarty rounds that fixed them. When a new hook reuses these helpers, the read/write-safety half of the audit is usually already closed — verify the *call site* passes the right mode/flags, don't re-derive the primitive's own safety from scratch every time.

**Git argument construction convention**: every `run_git([...])` call that takes caller-influenced path-like strings in this codebase puts a literal `"--"` before them (e.g. `git_helpers.py:1178`, `is_tracked_in_head`). This is the project's established pattern for "this string can never be reinterpreted as a git option" — check for it explicitly when reviewing a new `run_git` call site; its absence would be a real finding.

**gitmem word search on a brand-new file returns nothing found and that's normal**, not a red flag — see [[false-positives]] if this file gains history later. First audit of `unmassk-toolkit/hooks/stop-dod-gate.py` and `lib/git_helpers.py:is_tracked_in_head` was 2026-08-20; no prior notes existed.

**`lib/memory/` field round-trip pattern (verified 2026-08-22, `--issue` opened from M-only to all 7 note types, D-044/D-045)**: this pipeline enforces "no orphaned field" by construction — `vocabulary.py::FIELDS[name].reader` names the one real reader and the module crashes on import if a type declares a field without one. For `issue` specifically there are exactly three surfaces that must stay in sync and were all confirmed type-agnostic (no `note.type == "M"` gate left anywhere in `lib/memory/`): writer `format.py::_body_field_line`, human report `report_render_note.py::_note_fields`, and the boot safety net `health_plans.py::_issue_commit_dates` (regex-scans raw commit body `^Issue: #(\d+)$`, never calls `format.parse_message`, so it was already type-agnostic before this change). `validator_issue.py::validate_issue` (the real `gh issue view` existence check) also never branched on note type — the only gate that ever blocked non-M types from carrying `--issue` was `vocabulary.TYPES[...].allowed_fields`, now closed for all seven. `--issue` is `argparse type=int` at the CLI boundary in `bin/memory/note.py` — never a raw string reaching `gh` or the commit body — so injection-style findings don't apply (consistent with [[patterns]] top note); a bad/negative/nonexistent number fails loud via `RuntimeError` → exit 1, never a silently-written phantom trailer.

**Pre-existing gap found adjacent to this change, NOT introduced by it, out of diff scope**: `bin/memory/work.py --issue N` (work/checkpoint commits, `notes.write_work`) writes the same literal `Issue: #N` trailer but never calls `validator.validate_issue()` — no `gh` existence check before commit. A phantom issue number written this way still gets picked up later by `health_plans.py::plans_unreflected()` (which scans ALL commits, not just notes) and its `_last_activity_at()` will then fail every boot for that issue (`gh issue view` returns non-zero for a number that never existed) — surfaced as `plans_unreflected_error` (handled, not a crash) but the safety net stays permanently broken for that issue number. Not re-flagged as a new finding since `work.py`/`notes.py` weren't touched by this task's diff (`vocabulary.py`/`report_render_note.py`/`model.py` only) — worth surfacing if `work.py` or `health_plans.py` is ever in scope directly.
