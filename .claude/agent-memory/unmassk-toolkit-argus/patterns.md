**No external attacker in this repo's model.** CLAUDE.md states this explicitly (re-read and confirmed unchanged 2026-08-25) and it is load-bearing for every audit here: this toolkit is the owner's single-user tool, not a public product. OWASP-style hostile-input findings (injection from an untrusted network caller, auth bypass, CORS, etc.) are dead weight unless the finding is really about the system corrupting/losing its own state. The real threat model is **the system harming itself**: memory loss/corruption, writing outside the project root, a failure that passes silently, a badly-built command that self-executes on internal data.

**`git_helpers.py` is a mature, already-hardened shared library** (re-verified 2026-08-25: `run_git`/`open_no_follow_symlink`/`verify_path_within_project`/`ensure_runtime_dir`/`file_lock` all present and unchanged in shape). `run_git` (`Popen(["git"] + args, ...)`, never `shell=True`, process-group kill on timeout via `start_new_session=True`/`CREATE_NEW_PROCESS_GROUP`), `open_no_follow_symlink` (O_NOFOLLOW / Windows TOCTOU identity check / optional hard-link rejection / atomic replace variant), `verify_path_within_project` + `ensure_runtime_dir` (resolves every intermediate symlinked component, not just the final one) already carry inline `SEC-*`/`ROB-*` comments documenting prior Argus/Moriarty rounds that fixed them. When a new hook reuses these helpers, the read/write-safety half of the audit is usually already closed — verify the *call site* passes the right mode/flags, don't re-derive the primitive's own safety from scratch every time.

**Git argument "literal `--` before caller-influenced paths" convention — the concrete evidence for this is now GONE, principle unverified against any current production call site.** `is_tracked_in_head` (the function this was checked against, `git_helpers.py:1178`) no longer exists: it was deleted in the "fuera el guardián de tests del Stop" cleanup (commits `d70905a`, `5f6b513`), which also removed `hooks/stop-dod-gate.py` entirely. Only three remaining `run_git([...])` calls with a literal `"--"` exist at all, and they're in `tests/memory/*.py` against a *different*, test-local `run_git(args, cwd)` (3-value return) defined in `tests/memory/conftest.py:646` — not the shared `git_helpers.run_git`. **Still check for `"--"` before caller-influenced path args on any NEW production `run_git` call site** (the principle — "this string can never be reinterpreted as a git option" — is sound and worth holding new code to), but do not cite `git_helpers.py:1178` or `is_tracked_in_head` as the example again; both are gone.

**`lib/memory/` field round-trip pattern (established `--issue` opened from M-only to all 7 note types, commit `c186aa9`, re-verified 2026-08-25)**: this pipeline enforces "no orphaned field" by construction — `vocabulary.py::FIELDS[name].reader` names the one real reader and the module crashes on import if a type declares a field without one. For `issue` specifically there are exactly three surfaces that must stay in sync, all confirmed type-agnostic (no `note.type == "M"` gate left anywhere in `lib/memory/`, re-grepped 2026-08-25): writer `format.py::_body_field_line`, human report `report_render_note.py::_note_fields`, and the boot safety net `health_plans.py::_issue_commit_dates` (regex-scans raw commit body `^Issue: #(\d+)$`, never calls `format.parse_message`). `validator_issue.py::validate_issue`/`issue_exists` (the real `gh issue view` existence check) never branched on note type either — the only gate that ever blocked non-M types from carrying `--issue` was `vocabulary.TYPES[...].allowed_fields`, now open for all seven (confirmed: `issue` appears in every `allowed_fields` frozenset in `vocabulary.py`). `--issue` is `argparse type=int` at the CLI boundary in `bin/memory/note.py` — never a raw string reaching `gh` or the commit body — so injection-style findings don't apply (consistent with the no-external-attacker note above). **The gap once flagged here — `bin/memory/work.py --issue N` skipping the `gh` existence check — is CLOSED, fixed in the SAME commit `c186aa9` that opened the field**: `work.py` now imports `validator_issue` and calls `validator_issue.issue_exists(args.issue)` before committing (`work.py:53,137-148`), rejecting via `_issue_rejection` when `gh` confirms the issue doesn't exist. Re-verified 2026-08-25 — do not re-flag.

**`file_lock()` (git_helpers.py) is this repo's established fix for cross-process read-modify-write races — 18+ call sites use it** (memory notes/indexes/rules via `gitcmd.file_lock`, `incidents.py`, `install_apply.py`, `session-start-crew.py` via `claude_md_lock_path`, and as of the fix below, `checklist_state.py`). When a load→mutate→save cycle on a shared per-session/per-project file does NOT call `file_lock()` across the WHOLE cycle (not just the final write — `open_no_follow_symlink(..., atomic=True)` only protects a single write from torn/partial content, not two sequential writes racing each other), that omission is a real, checkable regression against the project's own convention. **The `checklist_state.py` instance of this gap (found 2026-08-24 on `lib/checklist_state.py`, hit via `checklist-gate.py`/`skill-checklist-inject.py` racing on `save_registry()`) is now CLOSED**: re-verified 2026-08-25, the module now exposes a `locked()` context manager (`checklist_state.py:139-170`) wrapping `file_lock()` around the full `load_registry()`→mutate→`save_registry()` cycle, with both call sites (`hooks/checklist-gate.py:171`, `hooks/skill-checklist-inject.py:135`) using `with checklist_state.locked(...)` around their read-modify-write. Do not re-flag this exact case; still check any OTHER new module with a load→mutate→save cycle for the same convention.

**`verify_path_within_project()` only guarantees "stays inside project_root somewhere" — it does NOT by itself pin a path to the specific intended subdirectory/file.** A caller-supplied path component (e.g. a session_id) containing `/` or `../` can pass the containment check while still colliding with a sibling file inside the guarded tree ("escapes the project" and "collides within the project" are different bugs — the guard only catches the first). **The `checklist_state.py` reproduction of this (session_id `"foo/../../bar"` aliasing a different registry file, found 2026-08-24) is now CLOSED**: re-verified 2026-08-25, `checklist_state.py:98-112` adds `is_safe_path_component()` (rejects `/`, `\`, `..`, empty) called before every path build (`registry_path()` line 122, `locked()` line 155) — its docstring literally names the `"foo/../../bar"` case this was written against. Do not re-flag this exact case. Still apply the general principle to any NEW path built from an identifier not already validated against a known format (UUID, etc.) upstream — check both failure modes separately.

**A `git commit` run directly via MY OWN Bash tool gets intercepted and rejected with the project's real "⛔ esto crea un commit fuera de gitmem" customs text — even inside a brand-new throwaway repo in scratch, with no local `core.hooksPath` and stock `.git/hooks/*.sample` only (verified 2026-08-26: `git config core.hooksPath` → not set, `.git/hooks/` → samples only, yet `git commit --allow-empty -m init` still got the canned rejection).** This is NOT a repo-level pre-commit hook — it fires regardless of which repo/cwd, which lines up with my own Bash Blacklist rule ("never run git commit") being enforced at the tool layer, not with anything in the code under audit. It does **not** block `git commit` invoked as a grandchild of a Python `subprocess.run(["git",...])` (shell=False) — that's exactly how `tests/memory/conftest.py`'s `tmp_repo`/`run_memory_script` fixtures create real commits, and the full suite (1255 passed) proves those aren't touched. **Consequence for reproductions:** never try a raw `git init`+`git commit` scratch repro from Bash again to test round-trip/commit behavior — it will always get intercepted and produce a misleading "aduana rejected it" signal that has nothing to do with the code being audited. Instead, either (a) call the production script directly as a subprocess (`python3 bin/memory/note.py ...` against a scratch repo whose initial commit was ALSO made via a script, not raw `git commit`), or (b) verify round-trip properties at the pure-function level (import `format.py`/`model.py` from `lib/memory/` with `sys.path.insert`, call `build_message`/`parse_message` directly) — the latter is what actually resolved the D-065/D-066 `Note.quote` round-trip check (quotes, embedded newlines, unicode, backslash+comma, a value that mimics a field label like `"Why: ..."`, whitespace-only — all round-tripped exactly via the existing `_fold`/`_fold_raw` mechanism, same one `Why`/`Description`/`Awaits` already use).

**`validate_issue_gate` (`validator_issue.py`, D-065/D-066, `Note.quote` field) audited 2026-08-26 — clean.** Verified: (1) the gate call in `bin/memory/note.py::main()` runs before ANY `notes.write`/`replace`/`promote`/`discard_alternatives` call, and `_build_context()` is read-only (zones/query/config loads only) — a gate rejection can't leave partial git/index state, confirmed by reading `main()` and by the existing test's own `before_count == after_count` assertion. (2) `note.quote` round-trip is lossless for special content (see repro note above) because it reuses the same `_fold`/`_parse_fields` mechanism already proven for `Why`/`Description`/`Awaits` — continuation lines always get exactly one leading space so an embedded line that looks like `"Issue: #5"` can never be mis-parsed as a new field. (3) grepped every `notes.write(`/`notes.replace(`/`notes.promote(`/`Note(type="Q"|"I"` call site outside `tests/`: only `bin/memory/note.py` constructs Q/I notes in production (`remove.py`'s only `Note(...)` is a hardcoded `type="R"` fence, not gated) — so there is no bypass path that creates a Q/I note without going through the gate. (4) `dataclasses.replace(note, ...)` in `notes.py`/`notes_promote.py` auto-carries `quote` since it's a real dataclass field — no risk of silent drop on promote/replace. No findings raised for this diff.

**`unmassk-trading/` is the one part of this repo where money is reachable, and its risk class is different from the rest of the toolkit.** Audited 2026-08-27 (first audit of the plugin). Three quirks that change how every future audit of it should run:

1. **The four gate/sizing scripts are lifted verbatim from tradermonty/claude-trading-skills and every one of them returns exit 0 for every verdict** — `check_circuit_breaker.py` exits 0 on `HALTED`, `check_pre_trade_discipline.py` exits 0 on `NO_GO` unless `--fail-on-non-go` is passed (the breaker has no equivalent flag at all), and `position_sizer.py` exits 0 while printing `Risk: $0.00 (0.0%)` when `--fractional` is omitted on a sub-1-unit crypto position. Verified by execution. `price_check.py` (the one script written here, not lifted) is the opposite and is correct: distinct exit codes 0/3/4/5. **Do not generalise price_check's discipline to the lifted three** — that assumption is exactly the trap the skill's own prose falls into.
2. **Absence of state is a PASS in the lifted breaker, corruption is a HALT.** `load_theses()` returns `EMPTY_STATE` for a missing directory, an empty one, or one with no `th_*.yaml`, and `EMPTY_STATE` → `TRADING_ALLOWED`; only `PARTIAL` (unreadable/duplicate files) halts. So a typo in `--state-dir` produces a green light, not an error. The lifted framework doc says so explicitly (`circuit-breaker-framework.md:75`) — the upstream project intended it. Any claim in this plugin's own prose that "missing data is never a pass" is false for the breaker and must be re-checked against the code, not the doc.
3. **In a skill, the fenced code block IS the executable, and this plugin repeatedly puts the safety in the prose two paragraphs below the block.** Recurring shape here: the copy-pasteable command omits the flag the surrounding text says is mandatory (`--output-dir`, `--journal-dir`, `--fractional`, `--circuit-breaker-decision`), so following the block writes report/journal files into whatever repo the shell sits in and skips the wiring that makes the gates talk to each other. When auditing this plugin, **read every fenced block on its own, as if the prose around it did not exist** — that is how a future Claude will use it.
